# 成就卡面设计 · v4（布局重排）

> 2026-10-23。原型：`.workbuddy/proto/achievements-cards-v4.html`（离线可跑，22 张真实卡）
> 箔层拆解：`docs/poke-holo-teardown.md`｜实验台：`.workbuddy/proto/poke-holo-lab.html`
> v3：配色按宝可梦实测（§8）｜v2：淡彩版，配色被判丑｜v1：墨线风，已废弃

## 一、v4 的边界：一个字都不碰特效

用户判定是「特效可以，UI 和布局不行」。所以 v4 的改动**全部落在排版**：

| 类别 | 是否改动 |
|---|---|
| 箔的色段宽度 / `color-dodge` 亮度基准 / 眩光半径 / 倾斜跟随系数 | **未动** |
| 稀有度的四档工艺映射 | 只把金卡静息箔 `.26 → .38`（见 §6） |
| 元素位置、间隙、字号、对齐、形状、色值 | 重排 |

唯一碰过的「特效」是 `--go`（金卡染色强度）`.32 → .16`，理由见 §6，那是**色值不是强度**。

## 二、五个量化诊断（不是形容词）

诊断方法：`playwright-cli run-code` 里跑 `getBoundingClientRect()`，把每个区块换算成相对 `.field` 的百分比与像素。224×313 的卡：

| 项 | v3 实测 | 后果 | v4 |
|---|---|---|---|
| 横向缩进 | `.art` 左 4.0% / `.wrr` 4.8% / `.cond` 5.5% | 三套左基准线并存，最大差 **3.4px**，肉眼就是「参差」 | 全部 `var(--px)` 一条线 |
| 字号档数 | 16/21/15/11.5/9/8.4/7.4/6.6/6.2/6/5.9 —— **11 档** | 四档挤在 6px 附近，印刷级精度缩到 1/3 就是噪点 | **5 档**：17 / 16 / 19 / 9.5 / 7.2 |
| 底部空白 | 条件区结束 79.7% → 三格开始 84.3%，**14.4px 无归属** | 下半截「松」，重量全掉到底边 | 条件区 `top`+`bottom` 双定位，空白归零 |
| 三格宽度 | 72.2 / 60.4 / 60.4 px（`flex:1` + `first-child:1.25`） | 不等分，整条银条看着是歪的 | `flex:1 1 0` 强制等分 |
| 条件区上下 | 上 2.1px / 下 18.6px | 同一段内容一头贴死一头悬空 | 上 8.7 / 下 10.4 |

**这五条是「不协调」的全部技术来源。** 没有一条是审美问题，都是可以量的。

## 三、网格：一条横线，一套竖标

```css
.card{
  --px: 4.4%;                       /* 唯一横向基准 */
  --pad-t: 2.6%; --pad-b: 2.2%;
  --g: 1.6%;                        /* 元件间 ≈4.6px */
  --g2: 3.4%;                       /* 段落间 ≈10px */
  --z-head: 10.5%; --z-art: 45%; --z-band: 5.2%; --z-wrr: 7.4%;
  --art-top:  calc(var(--pad-t) + var(--z-head) + var(--g));
  --band-top: calc(var(--pad-t) + var(--z-head) + var(--z-art) + 2 * var(--g));
  --cond-top: calc(var(--pad-t) + var(--z-head) + var(--z-art) + var(--z-band) + 3 * var(--g));
  --cond-bot: calc(var(--pad-b) + var(--z-wrr) + var(--g2));
}
```

纵向五带（相对 `.field` 高度）：

```
pad-t 2.6 ─ head 10.5 ─ g ─ art 45 ─ g ─ band 5.2 ─ g ─ cond（撑满 21.2）─ g2 ─ wrr 7.4 ─ pad-b 2.2
```

**两条硬规矩：**

1. **横向只认 `--px`。** `.zone.head / .zone.band / .zone.cond / .zone.wrr / .art / .zone.emb` 全部 `left:var(--px); right:var(--px)`。
   ⚠️ 写 `.zone.*` 时**必须同时给 `left` 和 `right`** —— 只给 `top` 的话，`position:absolute` 且无宽度会按内容 shrink-to-fit，四段会得到四个不同宽度（实测 61% / 51% / 59% / 52%），比不设更乱。
2. **竖向只用 `top / height / bottom` 的百分比。**
   ⚠️ **不要用 `padding` 百分比定位**：CSS 规范里 padding 百分比**恒相对宽度**，而 `height` 百分比相对高度。卡是 63:88，两者差 40%，混算必错位。

## 四、条件区为什么用双定位

条件区高度 = `.zone.cond` 的 `top` 到 `bottom` 之差，内容高固定（19px 数字 + 5px + 27.6px 说明）。

若只用 `top` + 固定 `height`，内容一多就溢出；若只 `top` + `bottom` 撑满，**剩余空间全堆在底部**（v3 实测下 18.6px）。

v4 的做法：`top` 和 `bottom` 都给（自动吸收总量变化），内部 `justify-content:space-between` 让大数字贴顶、说明贴底，**余量由我定的 `--g2` 决定，不由减法结果决定**。

## 五、字号：11 档砍到 5 档

| 层级 | v4 | v3 | 说明 |
|---|---|---|---|
| 名字 | **17px / 900** | 15px | 必须大于数字。宝可梦是名字 44 : HP 30 |
| PTS 数字 | **16px / 900** | 21px | 21 比名字还大，主次颠倒 |
| 条件大字 | **19px / 900** | 15px（`sm` 11.5） | 条件区的唯一主角 |
| 说明 | **9.5px / 600** | 9px / 500 | 压在中饱和场上，550 字重偏轻 |
| 标签（银条/三格/页脚） | **7.2–7.6px** | 5.9–6.6px | 屏幕下限 |

**删掉的信息件：**

- `LEGEND / EPIC` 稀有度胶囊 —— 银条里已有「传说」二字，胶囊是重复。
- **「解锁条件」红胶囊** —— 22 张卡全是这四个字，**信息量 0**，却是全卡最重的色块。宝可梦的 ABILITY 牌每张写的是不同特性名，那是信息；这个只是装饰。删掉后红色从全卡消失。
- 第三格「状态 进行中」—— 和「进度 2%」是同一件事的两种写法，unlocked 已由卡面明暗 + 徽记亮度表达。三格 → 两格（`进度` / `达成日`）。

**留下的取舍：** 宝可梦真卡 63mm 宽，底部那排 `illus.` 是印刷级精度（≈1.2mm 字高）。屏幕上 224px 等于缩到 **1/3.5**，那行字只剩 5px —— 那不是「小」，是糊。所以宁可删件，不留看不清的。

## 六、稀有度：金要出现在框上，不该洗掉类型色

### 6.1 金卡不再把场也染成金

v3 的思路是「整卡换材质」，把 `--fld*` 也调成金 —— 结果第一排 5 张金卡是一整片黄，类型识别一并丢失。

宝可梦金卡（VMAX）的真实做法是**框变金、插画照旧是彩的**。v4 只改 `.face.front` 的框材质，`--fld*` 一个不碰。

框色靠**明度**拉开（两者色相相同，靠色相区分不了）：
`#f3dc98 → #dcb85c → #c09639 → #a87f28`

### 6.2 `--go` 从 .32 降到 .16

`.gold` 层是 `mix-blend-mode: color` —— 它用金色的**色相 + 饱和度**直接替换底层的类型色，不保留明暗。`.32` 的强度下：

- 蓝场被染成**灰蓝**（金色色相替换了蓝）
- 橙场被染成**土橙**
- 结果：金卡和普通卡**都发脏**，而且金卡也不金

金应该出现在**框**和**箔**上。降到 `.16` 后类型色恢复准确，`--fo` 提到 `.38` 保证静息态就有金属。

### 6.3 金卡徽记必须是亮金，不能是深棕

v3 用 `stroke:#4d3a0c`（深棕刻线）。深棕刻线的语义是「金字上压出的凹槽」——**前提是底色为金**。

我们的金卡底色是类型色（深蓝/深绿/深紫），深棕压上去几乎看不见。v4 改 `#f7e3a4` 亮金 + 深色投影，在任何场色上都读得出「这枚徽记是金的」。

## 七、形状分工

| 元件 | 圆角 | 理由 |
|---|---|---|
| 卡面 | 9px | |
| 插画窗 | 6px | |
| 属性银条（`band`） | 999px 胶囊 | 宝可梦的插画下银条就是胶囊 |
| 数据银条（`wrr`） | 4px 直角 | **必须和 `band` 不同**：两条都做胶囊，一条是「属性标签」一条是「三格数据」，形状相同会让语义混在一起 |

## 八、特效层的定位方式改了一次（参数没动）

v3 的箔层用 `clip-path: inset(顶 右 底 左)` 裁到插画窗。问题是 `inset()` 的百分比基准和 `height` 的百分比基准不同，**一旦改内边距就会和窗子错位**。

v4 让 `.art` / `.shine` / `.zone.emb` 共享同一组 `left/right/top/height`：

```css
.art,.shine,.zone.emb{
  position:absolute;
  left:var(--px); right:var(--px);
  top:var(--art-top); height:var(--z-art);
}
```

物理上不可能错位，也不需要 `clip-path` 了。`epic`（整卡箔）单独覆盖一次 `top:0;bottom:0;height:auto`。

## 九、v2 → v3 → v4 演进

| 版本 | 结构 | 配色 | 结局 |
|---|---|---|---|
| v1 | 墨线 + 4px 硬投影 | 自调 | **被否**：「不要墨线风格」 |
| v2 | 宝可梦结构 | 自调淡彩 | **被否**：「配色好丑」 |
| v3 | 宝可梦结构 | 真卡像素采样 | 配色通过，**布局被否**：「不协调不精致」 |
| v4 | **重排网格 + 字号收敛** | 沿用 v3 | 通过，**已落地 1.5.0** |

**v3 的教训：结构对了不代表成了。** 色值可以从像素采，但间距、字号档数、形状分工这些「看不见的量」，采样采不出来，必须量自己的 DOM。

## 十、落地记录（1.5.0）

原型是独立的 HTML，落到 `apps/web` 时改了七处，每一处都是环境差异倒逼的，不是审美再调整：

| 改动 | 原因 |
|---|---|
| 类名全部加 `acard-` / `zone-` 前缀 | 原型里的 `.card` / `.face` / `.locked` / `.legendary` 在应用里会撞上全局面板样式；改用 `data-r` / `data-t` / `data-sc` 属性选效果，彻底不抢类名 |
| `--px` → `--card-px` | **全局 `--px` 是像素字体**（`'Press Start 2P'`）。同名的百分比变量把字体覆盖掉后，卡内 `font-family: var(--px)` 会静默失效 |
| 徽记映射改「**名字 → 内置 id → 类型 → 星形**」四层 | 库里 22 条成就有一多半是自定义的，**id 是 UUID 随机串**，按 id 映射必然落空 |
| 大字 19px → 16px | 真实进度文案是「当前最高技能 LV 1 / 20」这种长句（不是原型里手写的 `10 / 10000`），19px 在 186px 内宽下会截掉尾部的目标值 |
| 指针平滑从 rAF 循环改成 `@property` + `transition` | 变量注册成 `<percentage>` / `<angle>` 后 CSS 自己能插值，省掉一条常驻动画循环，也不怕 React 重渲染打断 |
| 新增 `flex-shrink: 0` 于 `.acard-big` / `.acard-text` | 条件区高度是「撑满剩余」，内容高度固定。不锁 shrink 的话剩余不足时会把 19px 的字压扁，再被自己的 `overflow:hidden` 裁成「拦腰截断」 |
| `.acard` 的 hover 抬升移到 `.acard-stage` | `.acard` 的 `transform` 已被 `rotateX/rotateY` 占用，两者会互相覆盖 |
| `.acard-big` 内容超长时保留省略号 | 兜底：自定义成就的进度文案可能更长 |

字段映射：

- `data-r` ← `rarity`（普通/稀有/史诗/传说 → common/rare/epic/legendary）
- `data-t` ← `type`（skill/attribute/project/milestone，未知归 milestone）
- `data-sc` ← **按列表索引轮转 6 种场景**（不是随机）：首屏稳定，且相邻两张必不同
- 大字 ← `achProgress(stats, condition).text`；进度格 ← `ratio`；达成日 ← `unlockedAt`
- `PTS` ← `points`；`NO.` ← 排序后索引（难度序）

同批完成的后端改动：

- `AchievementRepo::stamp_new_unlocks(ids, at)`：只写 `unlocked_at IS NULL` 的行，**永不覆盖**，返回写入行数（幂等判据）
- `achievements` RPC 在算出解锁集合后调用它，并把 `unlocked_at` 一并下发
- 回归测试 `backend/crates/soloup-store/tests/unlock_stamp_test.rs`（3 条：只写一次 / 空输入与未知 id / 批量只补 NULL）

## 十一、还没做的

- 金卡 5/22（23%）仍然偏多。原型有「后端稀有度（金 5）/ 建议重分级（金 3）」对照开关，**只改阈值不动 `pts`**，待拍板。实际库里 5 张金卡分值是 150 / 200 / 220 / 280 / 300，都在难度顶端，升序排列后落在最后两行，不像原型那样第一排整片黄。
- 22 张卡的下半部结构完全同构，「雷同感」只能靠徽记 + 场景 + 场色缓解，属产品结构问题（缺全画卡/异兽卡这类变体），不是布局能解决的。
