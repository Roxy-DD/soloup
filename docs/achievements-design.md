# 成就系统重构 · 设计与实施计划

> 状态：**设计稿，未动代码**。此文档只描述「要做什么、为什么、改哪里」，改完再补实施记录。
> 数据基线：2026-10-23，22 档成就，已解锁 8，总计 2320 分，`totalDays=14`、`streak=2`、`maxSkillLv=1.65`、`maxSkillCheckins=10`。
> 原型：`.workbuddy/proto/achievements-cards.html`（四档卡面效果，可交互）

---

## 0. 先说结论

现有成就系统有三个结构性缺陷，**不是「成就太少」，是「成就不可信」**：

| 问题 | 证据 | 后果 |
|---|---|---|
| **解锁时间从不落库** | 22 行 `unlocked_at` 全为 `NULL` | 卡面日期永远是「今天」→ 卡册失去全部记录价值 |
| **解锁可以倒退** | 判定 = 实时求值，`streak` 一断，「七日之约」就变灰 | 成就变成「当前状态显示」而不是「我拿到过」 |
| **有一条成就在数学上不可达** | `万时之功` 条件 `maxSkillCheckins >= 10000`，而该值单位是**天** | 27 年才能拿到；且名字说「万时（小时）」，单位和名字都对不上 |

所以这次重构的第一优先级不是加卡，是**让已有的卡变得可信**。加卡排在第二位。

## 1. 搜到的东西，只取能用的四句

查了三类资料（游戏成就分类 / 卡牌镭射实现 / 习惯类 App 的成就设计）。有参考价值的是：

1. **成就分四类，各有各的活**：进程引导（降低流失）、挑战高阶（提供长期目标）、趣味探索（制造惊喜）、社交展示（身份认同）。—— Soloup 没有第二个玩家，**第四类换成「轨迹」**：记录「你曾经是什么样的人」。
2. **三种死法**：为刷而刷（`击杀 10000 只哥布林`）、与核心行为脱节、只服务全收集型玩家。—— 现有 22 档里，`万时之功` 同时中了前两条。
3. **断签要有宽恕**：Duolingo 的 streak freeze 是它留存的核心，不是装饰。**断签就永久剥夺成就是设计事故**，不是难度。
4. **白卡面上画不出高光**（这条是我实测出来的，不是搜到的）：`mix-blend-mode: overlay` 和 `color-dodge` 在纯白底上数学恒等于白，等于没画。必须换成 `multiply`，且卡面底色要从 `#ffffff` 退到米白。原文照抄宝可梦那套实现会得到一个「没有效果的版本」。

## 2. 成就体系：四轴，不是四个 type

数据库已有 `type` 枚举（skill / attribute / project / milestone），**不动它**——改枚举要迁移，风险大于收益。改的是「按什么轴组织、每轴补哪些档」。

四轴的定义是「回答什么问题」，这比按对象分类更能指导加档：

| 轴 | 回答的问题 | 用到的统计量 | 现有档位 |
|---|---|---|---|
| **坚持** | 我能不能持续来 | `totalDays` `streak` `maxStreak` | 7 / 30 / 100 / 365、Streak 3 / 7 |
| **深度** | 我有没有真钻进去 | `maxSkillLv` `maxSkillCheckins` | Lv 1/2/4/10/20、10/50/200 天 |
| **广度** | 我是不是只走一条路 | `maxLitOneDay` `litSkills` `totalAttrs` | 2 / 4 / 全天 |
| **产出** | 我留下了什么 | `projectsCompleted` | 1 / 2 / 3 |

### 现存断层（要补的位置）

```
坚持  天数  7 —— 30 —— 100 —— 365       （7→30 空 23 天，缺 14）
      连击  3 —— 7 —— ✗                  （7 之后直接断了）
深度  等级  1 — 2 — 4 —— 10 —— 20        （4→10 跨度大，可接受）
      天数  10 —— 50 —— 200 —— 10000     （最后一档量级错误）
广度  单日  2 — 4 —— 全天(6)             （够了）
      幅面  ✗                            （缺「点亮过多少个不同技能」）
产出  项目  1 —— 2 —— 3                  （间隔太小，150/220/280 挤在一起）
```

### 补档清单（**只加不删**，共 +12 档，22 → 34）

| 轴 | 新档 | 条件 | 稀有度 | 分 | 为什么是这个数 |
|---|---|---|---|---|---|
| 坚持 | 两周 | `streak >= 14` | R | 45 | 7 天是「试试」，14 天是「习惯在形成」 |
| 坚持 | 月轮 | `streak >= 30` | SR | 120 | 跨过一个月，中间必然遇到至少一次想放弃 |
| 坚持 | 铁律 | `streak >= 100` | SSR | 260 | 100 天不断，这是身份级的事 |
| 坚持 | 最长一役 | `maxStreak >= 30` | SR | 110 | **断签不剥夺**：曾经连过 30 天就是事实 |
| 坚持 | 旧日 | `totalDays >= 730` | SSR | 320 | 两年，填 365 之后的空 |
| 深度 | 千锤（改） | `maxSkillCheckins >= 500` | SSR | 300 | 替换原 `万时之功`，见 §2.1 |
| 广度 | 十条路 | `litSkills >= 10` | R | 40 | 提醒「别只走一条」 |
| 广度 | 半张图 | `litSkills >= 20` | SR | 140 | 树的一半都摸过 |
| 产出 | 五作 | `projectsCompleted >= 5` | SSR | 320 | 1/2/3 太密，拉到 5 才够格当传说 |
| 产出 | 十作 | `projectsCompleted >= 10` | SSR | 480 | 长期天花板 |
| 轨迹 | 一年前 | `spanDays >= 365` | SR | 100 | 不看打卡数，只看「你在这条路上待了多久」 |
| 轨迹 | 归来 | 断签 ≥ 14 天后重新记录 | — | — | **暂不做**，见 §6 |

### 2.1 `万时之功` 怎么处理（需要你拍板）

现在三条都不对：条件 `10000`、单位「天」、名字说「时」。

三个选项：

- **A（推荐）改条件**：`>= 500`，改名「千锤」。语义成立（500 天打卡约等于 1000 小时以上），档位接在 200 之后。
- **B 换算成小时**：新增统计量 `maxSkillHours ≈ 天数 × 1.5`，条件 `>= 10000` 小时。要新增统计量、且 1.5 这个系数是编的。
- **C 原样保留**：承认它是彩蛋，不改。

我建议 A。但这是**改你已有的内容**，按规矩得你点头，我不擅自改。

## 3. 三个必须修的机制

### 3.1 `unlocked_at` 落库（P0，最重要）

**现状**：`achievement.list` 每次实时求值，返回 `unlocked: bool`，不写库。前端注释明说「`unlocked_at` 列不落库，面板按当天日期展示」。

**改成**：

```
1. 读库，取出 unlocked_at 非空的 id → persisted 集合
2. 实时求值 → achieved 集合
3. unlocked = persisted ∪ achieved      ← 单调，只增不减
4. 对 achieved - persisted 的每个 id，写 unlocked_at = 今天（本地时区）
```

三点必须守住：

- **单调性**：第 3 步的并集是核心。不并集，`streak` 一断成就就倒退，等于「成就」这个词失去了意义。
- **不覆盖**：已写的时间戳永不重写，即使条件再次达成。
- **本地时区**：必须用 `today_iso()`，不能用 UTC。跨时区/跨零点会写错日期。

**代价**：`achievement.list` 从纯读变成「读 + 偶尔写」。单用户 SQLite/WAL 下可忽略；但要用事务包住，且只在有新增时才 `UPDATE`。

**这条会破坏一个现有假设**：`docs/soloupmath.md` 里「成就纯实时求值」的表述要一起更新。

### 3.2 `maxStreak`（P0）

`streak` 是「从今天往回数」，断了归零。所以「连续 7 天」这类成就，断一次就永远补不回来——这是当前设计里最伤人的地方。

加一个统计量：遍历全部记录日期，求最长连续段。有了它，可以出「曾经连续过 N 天」的成就，断签不再抹掉过去。

**同时考虑宽恕机制**（可以只做前者，后者看你要不要）：

- 断 1 天算「缓冲」，`streak` 不清零，但显示一个标记。
- 这会改变「连续」的定义，属于产品决策，不是技术修补。**我倾向不做**：人生面板里「连续」就应该是连续，宽恕反而让记录不真实。保留 `maxStreak` 就够了。

### 3.3 新增统计量（P1）

| 统计量 | 算法 | 用途 |
|---|---|---|
| `maxStreak` | 全量日期求最长连续段 | 断签不剥夺 |
| `litSkills` | 记录里出现过的 distinct skill_id 数 | 广度轴 |
| `spanDays` | 今天 − 最早记录日期 | 轨迹轴 |

`projectsCompleted` 已有。`projectKinds`（项目类型多样性）需要先确认 Project 表有没有分类字段，**待核**。

## 4. 卡面效果（已在原型里跑通）

### 4.1 分级原则

**不靠换颜色分档，靠「要不要交互才反应」和「反应多大一片」。** 换颜色是最省事也最没说服力的做法——四张卡都是彩虹，只是深浅不同，玩家第一眼分不出来。

| 档 | 静态（不碰它） | 悬停 | 箔带宽度 |
|---|---|---|---|
| N 普通 | 无 | 光斑 + 暗角，内亮边 | 0（无箔） |
| R 稀有 | 无 | 光斑 + 斜向箔带 | 约 24% |
| SR 史诗 | 呼吸内辉 | + 点阵、扫描线 | 约 30% |
| SSR 传说 | **光带自己扫**（唯一动画） | 银箔 + 金框 + 亮反射带 | 约 26% |

关键：**SSR 不碰它也在动**，这是「传说」和「史诗」的分界线，比颜色可靠。

> ⚠️ 初版 SSR 是「金框 + 满幅彩虹 + 扫描线 + 点阵 + 5 颗闪星 + 内辉呼吸 + 棱镜层」，
> 一张卡上叠了 9 层、其中 4 个独立动画，实测被判定为「太花」「难看」。
> 现行版本砍到 4 层、只留 1 个动画，见 4.5。

### 4.2 四个技术要点（都踩过坑）

1. **`overlay` / `color-dodge` 在纯白底上恒等于白**——白卡面必须用 `multiply` 着色，底色还要从 `#ffffff` 退到米白/银灰，白光才有地方显形。
2. **`multiply` 只能压暗，永不出亮部**——只靠它，卡面会「闷」，没有任何金属反射。必须再叠一层同角度的 `screen` 白光带，才是「箔」。这是初版判难看的一半原因。
3. **箔光是斜带，不是圆斑**——圆斑边界会露出「这是个蒙版」的马脚。用 `linear-gradient` 蒙版，角度随光标微调，才像「卡是平的，只有某个角度反光」。
4. **箔面朝光标**反**方向**移动（`--mx = 1 - px`）——真实是光掠过表面。顺向会显得卡在追鼠标。

性能：全部 `transform` / `opacity` / `mix-blend-mode`，无 canvas、无 WebGL，`will-change: transform` 上 GPU。20 张卡同时 hover 不掉帧。`prefers-reduced-motion` 下全关。

### 4.3 顺手修的两处可读性问题

- **未解锁卡不再「几乎看不见」**：只削华丽度（去色），不削可读性。玩家得看得见条件才知道怎么拿——这是「目标清晰」的基本要求，现在 `opacity: .5` 把条件也一起削了。
- **标题加白描边**：箔带会从标题上路过，不加描边对比度会掉。

### 4.4 一个待定的视觉选择

未解锁卡：**A 全灰**（有稀缺感，现在这样）vs **B 保留极弱箔**（暗示「这张卡存在」）。

我倾向 A，但 B 在「卡册一屏灰」的时候观感更好。原型里可以切着看。

### 4.5 去「花」：从 9 层砍到 4 层

初版被判「太花」，逐层拆解后确认**问题不在颜色，在层数**。

**层级账（初版 → 现行）**

| 层 | 初版 | 现行 | 理由 |
|---|---|---|---|
| `.foil` 彩色 | 5px 粗彩虹条纹，满幅 | 大色块 conic + 斜带遮罩 | 细梳齿纹读作「棉布」，不是金属 |
| `.glare` 高光 | 径向光斑 | **同角度 screen 白光带** | 提供唯一亮部 |
| `.scan` 扫描线 | 0.55 | **删** | 高频纹理压在最上面，是「廉价」的主要来源 |
| `.grain` 点阵 | 4px 白点 0.28 | **删**（颗粒移到卡面基底） | 颗粒属于「材质」，不该是覆盖层 |
| `.sparks` 5 颗星 | 各自闪烁 | **删** | 装饰而非材质；5 颗 = 5 个动画源 |
| `.prism` 棱镜 | 0.5 | **删** | 与 foil 重复，纯叠加 |
| 内辉呼吸 | 2.2s 无限 | **删** | 金边本身已在「发光」，再呼吸就两处同时在动 |
| `.shine` 光带 | 3.6s / opacity .5 / 宽 64% | **6.8s / .3 / 宽 34%** | 唯一保留的动画：更慢、更细、更淡 |

**四条可复用的判断**

1. **同屏只能有一个动画源**。SSR 初版 4 个（光带 / 星光 / 内辉 / 扫描），眼睛找不到焦点 = 花。判据很简单：**把动画全关掉，卡还好看，才算设计过关**；靠动效撑起来的好看，是掩盖。
2. **元素数量比颜色浓度更决定「花」**。末轮把彩色 alpha 从 .30 提到 .62（浓度翻倍），观感反而更稳——因为同时把色带从「满幅」收进了 26% 宽的斜带。**同样的颜色，范围小十倍，就不花。**
3. **材质要分区**：真实高端卡的彩虹只从**边框/反光带**泛出，中心是哑光纸。整面同质铺满是「贴纸」。
4. **金属 = 明暗节奏，不是颜色**。同一个金色，从 `#fdf0bd` 渐变到 `#c69a38` 再回亮，才读作压出来的金属；纯色 `--yellow` 一律读作塑料。
5. **静息态不能是「全素」**。N/R/SR 静息位全素（无箔），SSR 静息留 40% 箔光——
   否则卡册一屏扫过时，最稀有的那张反而最暗。**稀有度的差，在「不碰它」的时候就该看得见。**
   注意选择器要写 `:not(:hover)` 且特异性高于 hover 规则，否则会被 hover 覆盖。

> 依据：Panini Prizm 的 base/silver 对照（base 是哑光银、silver 倾斜才泛虹彩）、
> 一位做过全息卡开发者的复盘（「整卡均匀施加同一效果」自评 lacklustre，改好靠**分区** +
> 「less was more」），以及高端印刷品设计的通行结论「选一种工艺做到极致，胜过堆满互相竞争的效果」。

## 6. 明确不做的

| 不做 | 为什么 |
|---|---|
| 社交类成就 | 没有第二个玩家，做了也是假的 |
| 断签宽恕 / streak freeze | 会让「连续」这个词失去意义，与面板的诚实原则冲突 |
| 「归来」成就（断签后回归） | 触发条件依赖「曾经断过」，现有统计量表达不了；要做得多加一个 `maxGap` 统计量，性价比低 |
| 成就总分做动态缩放 | 分数是绝对刻度，缩放会让历史记录失真 |

### 同批修掉的数据缺失：`unlocked_at`

`unlocked_at` 这一列从 v1 就有，但**从来没有被写入过** —— 成就判定一直是「每次请求按 condition 现算」，
算完就丢，日期没有落脚点，于是卡面上的「达成日」永远是空的，前端只能拿 `todayKey()` 顶上，表现为每张卡都是今天达成。

1.5.0 起：`AchievementRepo::stamp_new_unlocks` 在 `achievements` RPC 算出解锁集合后，把**尚未写入的行**补上
当天日期，**只写 NULL 行、永不覆盖**（断签或删记录导致条件不再满足时，达成日不该被抹掉）。
回归测试 `backend/crates/soloup-store/tests/unlock_stamp_test.rs`。

⚠️ 升级后首次打开时，所有历史已解锁成就的「达成日」都会被记为升级当天 —— 历史无法追溯。
